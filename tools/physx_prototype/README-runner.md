This experimental runner measures an authored PhysX field scene. It is not an EERSim backend integration and does not execute PROS, motors, sensors, or scoring logic.

Use `ovphysx==0.5.11`, its matched `ovstage==0.1.1.355824`, and NumPy. Compile `scene_inspect.cpp` against `physx/include` from the exact `ovphysx-0.5.11` source tag, as for the already validated cube helper:

```sh
g++ -std=c++17 -O2 -DNDEBUG -fPIC -shared -I physx-include scene_inspect.cpp -o scene_inspect.so
CUDA_VISIBLE_DEVICES="$(nvidia-smi --id='<gpu-index>' --query-gpu=uuid --format=csv,noheader)" timeout 180s .venv/bin/python benchmark.py --scene field.usda --work-dir field-gpu --probe-library scene_inspect.so --steps 240 --max-wall-seconds 60 > field-gpu.log 2>&1
CUDA_VISIBLE_DEVICES='' timeout 180s .venv/bin/python benchmark.py --backend cpu --scene field.usda --work-dir field-cpu --probe-library scene_inspect.so --steps 240 --max-wall-seconds 60 > field-cpu.log 2>&1
```

Replace `<gpu-index>` with the selected physical GPU index. The command resolves its UUID through `nvidia-smi` to avoid physical/CUDA numeric-order ambiguity. GPU mode requires a one-device CUDA mask and verifies live GPU dynamics, GPU broadphase, DirectGPU, a valid CUDA context and logical ordinal 0. CPU mode must run in a separate process; it forces CPU mode before instance creation. A small override layer selects GPU/GPU broadphase or CPU/MBP while preserving original asset reference resolution. Source scenes are not modified. Both runs request TGS with 100 position and 1 velocity iterations, verified against live actors. This matches the current numeric position-iteration budget, but PhysX TGS iterations and Bullet solver iterations are different algorithms.

`--threads` selects the CPU dispatcher worker count (default 2; range 0–255, with 0 executing tasks inline). `--dispatcher carbonite` is the default shared task-pool dispatcher; `--dispatcher native` selects PhysX's dedicated CPU dispatcher through `/physics/physxDispatcher`. Both apply to CPU host work even when dynamics run on the GPU. The runner sets `/persistent/physics/numThreads` before runtime creation, records requested dispatcher/count and actual `cpu_dispatcher_workers`, and requires the live worker count to match at initialization and completion. Recompile the inspector before using this runner. Carbonite can cap workers to its underlying task pool; a mismatch fails explicitly rather than publishing mislabeled timings. Use the native dispatcher when testing a worker count above that pool's limit.

The extra persistent setting is required for pinned ovphysx 0.5.11: its typed `num_threads` field writes `/physics/numThreads`, while native setup reads `/persistent/physics/numThreads`. A live check confirmed that requesting two workers through the typed field alone produced eight actual workers. Earlier results labeled two versus sixteen requested threads therefore do **not** establish a two-versus-sixteen worker scaling comparison. Retain those reports as historical throughput measurements with unverified actual worker counts; use fresh runs with the live getter for thread-scaling conclusions. The corrected runner keeps both settings aligned. See the pinned [typed config mapping](https://github.com/NVIDIA-Omniverse/PhysX/blob/ovphysx-0.5.11/ovphysx/src/ovphysx/ovphysx.cpp#L850), [persistent native setting](https://github.com/NVIDIA-Omniverse/PhysX/blob/ovphysx-0.5.11/ovphysx/ovruntime/include/omni/physx/IPhysxSettings.h#L65), and [dispatcher implementations](https://github.com/NVIDIA-Omniverse/PhysX/blob/ovphysx-0.5.11/ovphysx/ovruntime/source/omni.physx/plugins/Setup.cpp#L1374).

For a dedicated sixteen-worker comparison, add `--threads 16 --dispatcher native` to the same command and choose a fresh work directory. Keep the scene, backend, timestep, iteration counts and measured step count fixed when comparing dispatchers.

Optional `--position-iterations` (1–255) and `--velocity-iterations` (0–255) allow explicitly labeled convergence experiments; defaults remain100/1. Nondefault values require a matching exporter manifest so the override can set both scene limits and every dynamic actor before initialization. Live actor iteration counts must match the requested values. For example, select `--position-iterations 32` or `16` only after the geometry audit; performance at those settings does not demonstrate equivalent accuracy. Final velocities are saved in `final_velocities.npy`, with the same row order as `pose_rows.json`, and JSON reports maximum/RMS linear speed and maximum angular speed. This final diagnostic is outside measured loop time.

Default paths match the companion exporter: scene `/World/physicsScene`, rigid actors `/World/rigid_*`. An adjacent `field.manifest.json` is detected automatically (or select `--manifest`); the runner checks its scene SHA256, live collider/convex/triangle/joint and dynamic actor counts, and total dynamic mass. It requires the pose binding to cover every live dynamic actor and articulation link. It checks finite values, unit orientations, origins above−0.25m, and coordinates within 10 m. Those bounds and counts detect obvious failures; they do not establish contact accuracy, complete geometry/trajectory preservation, scoring behavior, or wheel friction equivalence. Inspect the exporter manifest and actual collider inventory before comparing performance.

Both backends first take one normal fixed-duration initialization step, then two configured warmup steps; all three are excluded from measured timing. The first pose sample is taken after that initialization step, at 1/240 s. This avoids `ovphysx 0.5.11`'s explicit/implicit GPU warmup, which performs a real 1 ns physics step and can inject unstable contact impulses into an initially touching scene. A normal `step_sync(dt)` marks GPU buffers ready before the first tensor read. The default measured run is 240 steps at 240 Hz; the wall budget is checked after complete steps and includes pose readback and statistics sampling. The shell timeout also bounds native initialization or a stalled native step. JSON separates initialization, synchronous measured physics calls, pose readback/validation, and total loop time. The dataset saves initial/final poses and samples public PhysX statistics every 60 steps. GPU memory buffer counters are lifetime high-water marks; some general counters may be unavailable or zero on a backend.

The native inventory includes static/dynamic actor, articulation/link, constraint and shape counts, masses, geometry categories, and actual convex GPU eligibility. `PxConvexMesh::isGpuCompatible()` accounts for cooking data and limits including 64 vertices and 32 vertices per polygon. Incompatible convex shapes may require CPU contact work even when the solver runs on GPU. Triangle mesh GPU cooking is not verified by this helper. Preserve native warnings: no all-GPU-contact claim should be inferred from scene flags alone.

To save actual cooked convex vertices and shape placements for an independent geometry audit, compile the companion `cooked_geometry.cpp` against the same headers and pass `--cooked-geometry-library cooked_geometry.so`. The runner resolves that path before changing directory, writes `cooked_geometry.json` after normal initialization, and reports the mesh/instance counts. Inspection is outside measured stepping time. It does not itself establish agreement with the authored mesh surfaces.

Audit saved joint constraints without running any simulation using NumPy and `usd-core`:

```sh
python audit_joints.py --scene field.usda --poses field-gpu/final_poses.npy --velocities field-gpu/final_velocities.npy --rows field-gpu/pose_rows.json --output field-gpu/joint-audit.json
```

The audit uses authored USD joint frames, static transforms, and final dynamic world poses. Velocity tensors must contain world COM linear velocity followed by world angular velocity at that same timestep. It reports forbidden anchor translation, rotation, anchor velocity and angular velocity for fixed, revolute and prismatic joints. Defaults of 1 mm and 0.5 degrees are explicit diagnostic pose tolerances, configurable with `--translation-tolerance-m` and `--rotation-tolerance-deg`; they are not a demonstrated accuracy standard. Velocity residuals are reported without an arbitrary pass threshold. Exit code 1 means a configured pose check failed; JSON preserves each joint's measurements and input hashes. A passing audit still does not establish joint-limit, contact, damping or trajectory fidelity.

The recorded v3 CPU and GPU snapshots both fail the four toggle joints: maximum forbidden translation is approximately 36.3 mm on CPU and 35.1 mm on GPU, with maximum hinge-axis tilt approximately 7.30 and 6.87 degrees respectively. CPU final velocities are zero while GPU retains large forbidden velocities. The corrected v4 export resolves those four filter failures; all 13 joints pass the configured pose checks in the five final runs. See the current [results](../../docs/physx-prototype-results.json). Throughput and final joint checks still do not establish contact or trajectory equivalence.

All generated layers, cooked mesh/CUDA caches, XDG directories and temporary files are directed into `--work-dir`. Preserve the reports and input hashes before removing an experiment's work directory. Source assets remain separate from generated outputs.
